# OS LAB – Operating System Simulator and Visualizer

An interactive laboratory for learning Operating System concepts. Students enter their own inputs, watch each algorithm run
step by step, compare algorithms on identical workloads, read lessons, take quizzes and use a safe simulated terminal.
Everything is a **simulation**: nothing here touches your real processes, memory, disk or files.

* **Frontend:** React + TypeScript + Vite + Tailwind CSS
* **Backend:** Python + FastAPI (the algorithms are plain, separately tested Python modules)
* **Storage:** SQLite file for accounts and admin data (created automatically)

---

## 1. What is inside

**Welcome page**: The welcome page gives an overview of the platform, with shortcuts to all 10 modules, the Learning Center, the Terminal and the Quizzes.

**CPU Scheduling**: You can run FCFS, SJF, SRTF, Round Robin, preemptive and non-preemptive Priority, Multilevel Queue and Multilevel Feedback Queue scheduling. Each run shows a Gantt chart, the ready queue, per-process and average metrics, and a comparison between algorithms.

**Process Management**: You can watch a process move through its lifecycle with Process Control Blocks and a 5-state diagram, see context switches and the process tree, and try inter-process communication (pipe, message queue and shared memory) and threads.

**Process Synchronization**: You can explore race conditions, critical sections with a mutex, binary and counting semaphores, producer-consumer, readers-writers and dining philosophers, and run each scenario both with and without synchronization.

**Deadlock Management**: You can run Banker's safety check and request test, detect and recover from deadlocks, view the resource allocation graph, and load ready-made scenarios.

**Memory Management**: You can compare First, Best and Worst fit using fixed or variable partitions, free memory, run compaction, and see fragmentation.

**Page Replacement**: You can run FIFO, LRU, Optimal, LFU and Clock, and see the frame table, a hit and fault timeline, a comparison, and a demonstration of Belady's anomaly.

**Disk Scheduling**: You can run FCFS, SSTF, SCAN, C-SCAN, LOOK and C-LOOK, watch the disk head move as an animation, and compare the algorithms.

**File System**: You can use contiguous, linked and indexed allocation on a virtual disk, build directories, inspect the block map, and compare the methods.

**Virtual Memory**: You can follow address translation, the TLB, demand paging and page faults, and study the working set and thrashing.

**Performance Analyzer**: It is also the top-bar Compare page. It runs several algorithms on the same workload across six categories and shows charts, recommendations computed from the real results, a downloadable report, and saved comparisons.

**Terminal**: The terminal is a command line over one simulated operating system, covering processes, memory, disk, the file system, the scheduler and a deadlock check. It accepts only a strict list of allowed commands.

**Learn**: The Learning Center has 30 lessons, at beginner, intermediate and advanced level for every module, with worked examples and quizzes. The quiz's numerical questions are generated by the simulators, and your progress is tracked.

**Accounts**: Anyone can register and sign in. Guests can still use every simulator, and signed-in students also get saved progress and quiz history.

**Admin**: Administrators get analytics, user management, management of lessons and quiz questions, student performance reports, and an audit log.

Every simulator has: an input panel, play / pause / previous / next / reset and a speed slider, a visualization suited to that
algorithm, a step-by-step explanation of *why* each decision was made, results, and (where it makes sense) a comparison.
All results are calculated by the backend; the browser only draws them. Changing the animation speed never changes a result.

## 3. Quick start

Open the `os-lab` folder in a terminal (in VS Code: *Terminal → New Terminal*). You need **two terminals running at the same time**.

### Terminal 1 – backend (API on http://localhost:8000)

**Windows (PowerShell)**
```
cd backend
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

**Linux / macOS**
```
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

It is ready when you see `Uvicorn running on http://127.0.0.1:8000`.
If PowerShell refuses to activate the environment, run `Set-ExecutionPolicy -Scope Process Bypass` and activate again.
Interactive API documentation is at http://localhost:8000/docs.

### Terminal 2 – frontend (app on http://localhost:5173)
```
cd frontend
npm install
npm run dev
```

Open **http://localhost:5173**. You land on the welcome page; use the cards, the top bar or the sidebar to open a module.

### Next time
Only start the servers again (activate the environment, then the `uvicorn` command; then `npm run dev`).
`python -m venv`, `pip install` and `npm install` are needed only once (and `pip install` again whenever `requirements.txt` changes).

## 4. Create your administrator (once)

Accounts are stored in a SQLite file, so the admin account has to be created first. Open a **third** terminal:

```
cd backend
.venv\Scripts\Activate.ps1          (Linux/macOS: source .venv/bin/activate)
python -m app.auth.create_admin
```

It asks for an email, a username and a password (typed hidden; at least 8 characters with letters and digits).
Then in the app click **Sign in** (top right), sign in, and open the **Admin** tab.

*Alternative:* set `OSLAB_ADMIN_EMAIL`, `OSLAB_ADMIN_USERNAME` and `OSLAB_ADMIN_PASSWORD` in the backend terminal before running
`uvicorn`; the first administrator is created at start-up if none exists yet.

Students register themselves with **Sign in → Create account**.

## 5. Using the application

### Simulators
1. Choose a module (welcome page card or sidebar).
2. Pick an algorithm and enter your inputs (examples are pre-filled).
3. Press **Start Simulation**. Use ⏮ ⏯ ⏭ ↺ and the speed slider, or click any line in the step list to jump to it.
4. Read the explanation of each step, then the results and metrics.
5. Use the **Comparison** section to run several algorithms on the same input.

### Performance Analyzer / Compare
Pick a category (CPU, paging, disk, memory, file allocation, virtual memory), edit the workload, tick two or more algorithms and press
*Compare*. You get a table (best value in green, ties left unmarked), a chart, an explanation of why results differ, and recommendations
derived from the actual numbers. **Download report (.md)** creates a report; **Save in this browser** keeps the comparison locally.
No algorithm is declared universally best; the winner depends on the workload and the metric.

### Learn
*Lessons* (read, try the practice question, open the matching simulator, mark complete), *Quiz* (choose module and level, optional timer;
correct answers are shown only after you submit) and *Progress* (completion per module, quiz history, topics that need practice).
Signed-in students' progress and quiz attempts are also stored on the server.

### Terminal
Type `help` for the list. A short tour:
```
process create P1 5 1 100        create a process: burst 5, priority 1, 100 KB of simulated memory
process create P2 3
process list
scheduler run rr 2               run all ready processes with Round Robin, quantum 2
memory status
filesystem mkdir /docs
filesystem create /docs/a.txt 3  creates a 3-block file on the virtual disk and generates disk requests
filesystem read /docs/a.txt
disk status                      head position and total head movement under FCFS / SSTF / SCAN / LOOK
deadlock load deadlock           safe | unsafe | deadlock
deadlock check
history
clear
```
Other commands: `os-info`, `process status <pid>`, `process terminate <pid>`, `cpu status`, `filesystem list [path]`,
`filesystem delete <path>`, `filesystem format <contiguous|linked|indexed>`. Use ↑ / ↓ for command history.
Shell characters (`; | & $ \` > <` and quotes) are rejected before parsing; only the commands above exist.

### Admin dashboard
* **Overview:** students, administrators, active and inactive accounts, simulation executions, most-used modules, simulations per day,
  quiz attempts, participants and average score, learning completion.
* **Users:** search and filter, make admin / student, activate / deactivate, reset password, delete.
* **Content:** create, edit, delete, publish or hide lessons and multiple-choice quiz questions. Built-in items can be hidden but not deleted.
* **Performance:** per-student quiz and lesson statistics and a completion report per module.
* **Audit log:** every sign-in event and every administrative action.

All figures come from recorded activity (simulation requests, graded quizzes, completed lessons); nothing is estimated.

## 6. Security

* Passwords are hashed with **Argon2id** (falls back to scrypt if `argon2-cffi` is not installed). Plain passwords are never stored or logged.
* Sessions: a short-lived access token kept only in memory, plus a rotating refresh token in an **httpOnly, SameSite=Strict cookie**.
  Refresh tokens are stored only as hashes; reusing an old one later revokes all of that user's sessions.
* Five wrong passwords lock an account for 15 minutes; sign-in and sign-up are rate-limited per address.
* Roles are read from the database on every request, so deactivating or demoting someone takes effect immediately.
* Every admin route requires an administrator, enforced on the server (401 for guests, 403 for students).
  An administrator cannot change or delete their own account or remove the last active administrator.
* All database access uses parameterised SQL. The virtual file system only accepts a strict path pattern and never touches host files.
  The terminal never runs host commands, scripts, SQL or `eval`.
* Inputs are bounded (see Limits) and simulations are deterministic. The API applies a per-address rate limit.
* Serving over HTTPS? Set `OSLAB_COOKIE_SECURE=1`.

## 7. Configuration (environment variables, all optional)

| Variable | Meaning | Default |
|---|---|---|
| `OSLAB_DB_PATH` | SQLite file | `backend/data/oslab.db` |
| `OSLAB_DATA_DIR` | Folder for the database and the generated token secret | `backend/data` |
| `OSLAB_JWT_SECRET` | Token signing secret, at least 32 characters. If unset, a random one is generated once and kept in the data folder | generated |
| `OSLAB_COOKIE_SECURE` | `1` to mark the session cookie Secure (HTTPS) | off |
| `OSLAB_CORS_ORIGINS` | Comma-separated allowed browser origins | `http://localhost:5173,http://127.0.0.1:5173` |
| `OSLAB_RATE_LIMIT` | API requests per minute per address | `600` |
| `OSLAB_ADMIN_EMAIL`, `OSLAB_ADMIN_USERNAME`, `OSLAB_ADMIN_PASSWORD` | Create the first administrator at start-up | none |
| `VITE_API_URL` (frontend) | API base URL instead of the dev proxy | `/api/v1` |

Never commit real secrets. The `data/` folder and `.env` are already in `.gitignore`.

## 8. Tests

```
cd backend
pytest                           # full suite (after pip install -r requirements.txt)
python run_tests_offline.py      # no installs needed: every engine, security rule, contract check
```
The offline runner skips the HTTP tests that need FastAPI; `pytest` runs everything, including `tests/test_api_*.py`.

What is covered: every algorithm against textbook or hand-calculated results; deterministic concurrency scenarios; the terminal's
allow-list and injection attempts; password, token, session and admin logic; that every admin route requires an administrator; that every
route and data shape the frontend uses matches the backend; and numbers quoted in the lessons.

Frontend type check and production build (needs `npm install` first):
```
cd frontend
npm run build
```

## 9. Limits (to keep the server safe and fast)

Up to 100 processes, 500 references or requests, 512 disk blocks and 200 operations per run. Each simulation returns at most 5,000 recorded
steps (metrics and charts always cover the whole run). Quizzes allow up to 60 questions per submission.

## 11. Optional: PostgreSQL + pgAdmin

The original plan used PostgreSQL. The tables, Alembic setup and seed data exist (`backend/app/db`, `docker-compose.yml`) but **the app
currently stores accounts in SQLite and does not use PostgreSQL**, so you can ignore this section. To try it anyway (needs Docker):
```
copy .env.example .env           (Linux: cp .env.example .env)   then edit the passwords
docker compose up -d
cd backend
alembic revision --autogenerate -m "initial schema"
alembic upgrade head
python -m app.db.seed
```
pgAdmin is then at http://localhost:5050 (server host `db`, port 5432, credentials from `.env`).

## 12. Troubleshooting

| Problem | Fix |
|---|---|
| Page says "Cannot reach the backend" | Start Terminal 1 first. Test http://localhost:8000/api/v1/health |
| `ModuleNotFoundError` (fastapi, sqlalchemy, argon2, …) | Activate the environment (`(.venv)` in the prompt) and run `pip install -r requirements.txt` again |
| PowerShell blocks `Activate.ps1` | `Set-ExecutionPolicy -Scope Process Bypass`, then activate again |
| Port 8000 is busy | Use `--port 8001` and change the `"/api"` proxy target in `frontend/vite.config.ts` |
| `npm install` fails | Check `node --version` (18+). Delete `frontend/node_modules` and retry |
| Admin tab says "Sign in required" | Sign in with the administrator you created in step 4 |
| Forgot the admin password | Run `python -m app.auth.create_admin` to add another admin, or delete `backend/data/oslab.db` to start fresh (this removes all accounts and saved data) |
| "Too many failed attempts" | Wait 15 minutes, or have an administrator reset the password |
| Signed out unexpectedly after a restart | Normal if `backend/data` was deleted; otherwise sign in again |
| `npm run build` shows a type error or a page misbehaves | Note the exact message; see STATUS.md for what has and has not been verified |

## 13. Honest status

Everything described above is implemented and has automated tests, **except** that the web layer has not been exercised in a real browser
by the author's test environment (no network access there): `npm install`/`npm run build`, live cookie handling and animations are the
parts to watch on first run. `STATUS.md` lists exactly what was verified, what was not, and the known gaps.

Known gaps: Admin cannot yet manage the list of modules or algorithm descriptions; paging and segmentation are not simulated under Memory
Management (see Virtual Memory); deadlock prevention is explained but not simulated; readers-writers implements reader preference only;
terminal sessions live in server memory and are lost on restart; there is no Docker image for the app itself.
